# Owner answers

Decisions the owner gave on 2026-11-14. They override every design and `owner-questions.md`. Not committed to
the `rebuild` branch.

## Answered by the owner

| # | Question | Answer |
|---|---|---|
| A1 | The two fields of `PerParticleVelocity` (Q1, naming review O3) | `for_next_step` (kept on the particle for the next step) and `for_this_step` (moves the particle in this step). `state` and `travel` are no longer field names. Related decided names that contain `travel` (`own_motion_in_travel`) keep the word `travel`. |
| A2 | Error with context (Q2) | `<Module>Failure { <Module>Error error; ...context }`, returned through `std::expected<T, <Module>Failure>`. |
| A3 | The word `place` (Q6) | Accepted: `CellPlaceIndex`, `FacePlaceIndex`, `CornerPlaceIndex`. Add the glossary row. |
| A4 | Material words (Q7, naming review O6) | The plain set: `springy_stretch`, `springy_deformation`, `permanent_volume_change`, `internal_force_per_area`, `deformation_rate` with `stretch` and `shear`, `rest_volume`, `volume_ratio`, `MaterialKind::kSpringySolid`, `friction_angle`, `cohesion`. The textbook word is given once in the comment. |
| A5 | Who runs the joint velocity-and-pressure solve (Q16, conflict C1) | Viscosity runs it. The `VelocityResponse` hook is removed from pressure. |
| A6 | Names of the two solves | `pressure::SolvePressure` (scenes with no viscous ingredient; its docstring says so) and `viscosity::SolveViscosityAndPressure` (replaces `ApplyViscosity`). The step stage is named after the function that runs. |
| A7 | Raw weight where cell sizes mix (Q19) | The uniform quadratic curve in the particle's cell width times the face piece's area share, weights divided by their sum, fit with the measured weighted spread. |
| A8 | Do different materials share one grid velocity (solids question 1) | No. Materials that do not mix are separate sets with their own face sums; `CollideSolids` applies the contact rule at shared faces. Transfer's stages and `ComputeCellsFromParticles` take a material-subset input. |
| A9 | Sand | Left out of the main sequence. Sand becomes the last module, after the Blender add-on: "important but not mandatory". Materials ships liquid, gas, snow and springy solid. The sand design text is kept and moved to the sand module. |
| A10 | Gas and liquid in one scene | Supported from the start. The gas module designs, builds and tests gas beside liquid (gas boundary at the liquid surface, markers kept out of the liquid's sums, smoke over a moving water surface), and the needed changes in pressure, transfer and particles are made in those designs. |
| A11 | Math helper names | Short nouns in `namespace math`: `math::Dot`, `math::Cross`, `math::Transpose`, `math::Determinant`. |
| A12 | The run-on check | `CheckCanRunOn(RunOn)`. `RunOn` is the caller's choice; nothing ever changes it silently. |
| A13 | Plumbing names | `ToMessage(error)`, `FLUIDITY_CPU_AND_GPU`, `std::expected` used directly with no alias. |
| A14 | Output file formats | Use open formats as much as possible: Alembic, USD and OpenVDB. Everything a person or another program plays back or renders (particles, surface, foam and spray, volumes, solid motion where a format carries it) is written in one of these, readable with the add-on disabled. FluidiTy's own array file is used only for what no open format fits: the saved state and internal run records. Where two open formats could carry a product, pick the one Blender's native reader consumes fully (velocity for motion blur, per-point and per-face attributes, a file sequence), proven by a test in Blender, and prefer USD when both pass. |
| A15 | Batched runs | The pressure, viscosity and gas solves are also batched, so a scene far larger than GPU memory can run (limited by CPU memory). A batched run agrees with a one-piece run within the solver's tolerance, not byte for byte; each mode is repeatable on its own (same input, same bytes). This replaces "the solves are not batched" and the byte-identical test between modes. (2026-11-14) |
| A16 | Blender and GPU targets | Blender 5.3 is the one supported version (5.2 was removed from the development machine). The GPU build contains code for RTX 30, 40 and 50 series (`sm_86`, `sm_89`, `sm_120`), stated as "tested on RTX 5060 Ti; compiled for RTX 30 and 40, unverified". (2026-11-14) |
| A17 | Grid build on GPU runs | The grid is built on the GPU in a GPU run; only a small status record comes back. The CPU builder serves CPU runs and is the oracle the GPU tables are compared with bit for bit. Principle stated by the owner: a run is all CPU or all GPU; transfers between them are costly. (2026-11-14) |
| A18 | Correctness over lag | Where a design applies a coupling one step late (gas pressure on liquid; liquid pressure on snow and springy solids), the owner accepts changing the algorithm for correctness. Pending the literature check: sealed gas and blocking materials go inside the pressure solve. (2026-11-14) |
| A19 | Tool and library versions | Use the latest released versions of clang-format, clang-tidy and the open-format libraries (Alembic, OpenVDB, OpenUSD and their dependencies), pinned to whatever resolves; no need to match Blender's bundled versions. (2026-11-14) |
| A20 | Wind | The add-on reads Blender's own Wind force field (as the gas branch did) and converts its strength to an acceleration with a documented factor; aim to be compatible with Blender force fields. (2026-11-14) |
| A21 | Proofs | Install Lean and an independent kernel checker from the Lean Kernel Arena on the development machine so proofs are checked, not only written. (2026-11-14) |
| A22 | Ordinary words in the glossary | Chosen word by word on 2026-11-14: `system`, `link`, `store`, `stored`, `core`, `lower`, `upper`, `head`, `tail`, `parent`, `children`, `coarse`, `support`, `node`, `accept`, `install`, `compatible`, `reserve`, `resolution`, `epsilon` and `storage` are banned only in their fluid-jargon meaning (the meaning their glossary row replaces); ordinary English use is allowed in comments and names. In the glossary each gets a qualifier naming the banned sense, so the rules check prints a note, not a failure. `budget` is allowed for a planned cost shown to the user (memory budget, time budget); a hard limit is still `max_...`. Renames already made for these words stay where the old name was the jargon sense (`GridBuffers`, `InternalForceTotals`, `CapabilityLevel`, `KeptFrameInputs`). |
| A23 | The memory estimate's line type | Not "row", and not a bare "entry" (it is not an entry of memory). `MemoryRow` becomes `MemoryEstimateEntry` (owner's choice among MemoryPlanEntry, MemoryEstimateEntry, MemoryDiagnosticEntry, PlannedArray). Every `Build<Module>MemoryRows` becomes `Build<Module>MemoryEstimate` and returns the module's entries; fields, parameters and comments say "memory estimate" for the list and "entry" for one line (`output_rows` -> `output_estimate`, `cell_resize_rows` -> `cell_resize_estimate`, `grid_memory_rows` -> `grid_memory_estimate`). The glossary keeps "row" for a matrix row only and drops the "memory row" allowance. (2026-11-14) |
| A24 | Blocking materials and sealed gas beside a viscous liquid | Extend the viscous solver: `viscosity::SolveViscosityAndPressure` carries the blocking-material face terms and the sealed-gas term, as the pressure solve does (A18). No excluded combination, no one-step-late path. (2026-11-14) |
| A25 | What makes a liquid viscous | The setting decides and the grid number advises. A liquid is viscous exactly when its viscosity setting is above 0, fixed for the whole run; the water preset has viscosity 0, so water scenes use `pressure::SolvePressure`. `check` and the run's start print, per liquid, the grid-based number (viscosity x step / (density x smallest cell size squared)) and a note when a viscous liquid's number is so small that viscosity changes nothing visible, advising to set it to 0. The path never switches during a run. (2026-11-14) |
| A26 | A viscous liquid against snow or a springy solid | It sticks. The material's face velocity is an unknown of the viscous solve, so the two are coupled tangentially as well as in the normal direction (as in Zarifi and Batty 2017 and Fang et al. 2020). Not a contact rule applied after the solve. An inviscid liquid keeps the existing rule. (2026-11-14) |
| A27 | Free solids beside a viscous liquid | Lifted too: a rigid body moved by the liquid has its velocity (linear and angular) in the viscous solve. No combination of materials is refused because of viscosity. (2026-11-14) |
| A28 | `StepRequest` | Renamed `StepInputs`. Naming rule 9 has no exception for `Request`. (Review of the Foundation rulings, 2026-11-14) |
| A29 | Verbs | `Copy` is allowed (copies values between two arrays on the same processor). `Release` is not. `Free` is allowed for freeing memory (`FreeBufferBytes`), and `Take` for getting preallocated buffers back out of an object that is no longer needed (`TakeBuffers(StaggeredGrid&&)` replaces `ReleaseBuffers`). (2026-11-14) |
| A30 | Buffers on different processors | Made impossible rather than reported: functions that take two buffers (or a buffer and its working buffers) require the same processor as a documented precondition, checked by an assertion in debug builds. `BufferError::kRunOnMismatch` is removed, and modules have nothing to map. (2026-11-14) |
| A31 | The word 'scratch' | Not used. Reusable working memory is 'buffers', as the glossary already defines the word (preallocated, reused every step) and as the modules use it: `OrderBuffers`, `SumBuffers`, `BuildOrderBuffers`, `BuildSumBuffers`, `ComputeOrderBuffersSize`, `ComputeSumBuffersSize`. Every function that needs working memory has ONE form, which takes its buffers; the convenience forms that built their own are removed. Module names follow (`GridScratch`, `TransferScratch` and similar are renamed with 'Buffers'). (2026-11-14) |
| A32 | How `Buffer<T>` reaches the GPU | Kept as built (typed templates in `buffer.h` over untyped byte functions in `buffer_bytes.h`, defined in one source file), with a clearer explanation: a three-line statement and a small two-layer diagram in the header comment and the paper. (2026-11-14) |
| A33 | Other Foundation rulings | Approved as built: R1-R6, R8, R9, R11-R14, R16-R23, R25, R27, R29-R35, R37-R40, the final state of R10 and R15 (no allowed-name exemption for `MoveParticle` until the contact module declares it; no test name contains 'And'), 'thread block', and the names `RunOnCallStatus`, `LaunchSize`. (2026-11-14) |
| A34 | Planning files in git | Committed on the local branch `rebuild-planning` (from `main`), one commit per planning pass; `main` and `rebuild` untouched; nothing pushed. Script: FluidiTy-rebuild/.superpowers/sdd/commit-planning.sh. (2026-11-14) |
| A35 | Early Windows check | The owner runs `pwsh -NoProfile -ExecutionPolicy Bypass -File tools/run_gpu_tests.ps1` once on the Windows machine after Foundation and pastes the block back; the real run still happens at the end. (2026-11-14) |
| A36 | Same bits on CPU and GPU | As built: discrete outputs always equal; floating point within a tolerance except functions whose header promises same bits unless NaN (Foundation's and the eleven module promises). (2026-11-14) |
| A37 | Grid room on the GPU | As planned: no default; planner-sized with 25 % headroom; build working buffers exist once and are lent; outgrowing the room stops with a raise-limits result. (2026-11-14) |
| A38 | Known-open tests | `DISABLED_` prefix plus a second registration as an expected failure under the label `known_open`, listed in docs/known-open-physics.md; the gate runs that label. (2026-11-14) |
| A39 | Commit attribution | No `Co-Authored-By`. Each commit ends with one `Assisted-by: Claude Code:<model id>` line per model that worked on it (kernel style; for example `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-fable-5-2` for the session that directed and reviewed), then the `Claude-Session:` line. The owner is the sole author. Applies to `rebuild` and `rebuild-planning`. (2026-11-15) |
| A40 | Resuming a run | The resumed run reuses the recorded run mode. If that mode no longer fits in memory, the resume refuses with a clear message and names the flag that continues in another mode on purpose. (2026-11-15) |
| A41 | Choosing the size of new cells | One shared size rule, written once and run on either processor, with fixed inputs (distance to the surface, to solids, to user regions, a refinement map). No CPU callback, no copies for it, no CPU grid copy kept for it in a GPU run. (2026-11-15) |
| A42 | Constants and viscous modelling choices | Accepted: one solve piece may use 25 % of the GPU budget (4 values per cell of direct-solve room in that layout); only a band of material (1.5 cell widths) is solved with a viscous liquid; where two materials share a face the heavier one is what the liquid sticks to. Not accepted as proposed, asked again: the warning margins (+10 % memory, +25 % copies), the viscous-effect threshold 2.5e-4, the 70 % GPU budget with 1.25 grid headroom, guided solids holding forbidden motion, no drag total for driven plates. (2026-11-15) |
| A43 | End-of-run warnings | A planned budget is a promise: any measured value above its planned budget (peak memory on either processor, copies per step) prints a warning with the amount. No margin constants. The planner's numbers must therefore be true upper bounds. (2026-11-15) |
| A44 | Advice to set viscosity to 0 | Judged over time, not per step: `check` advises it only when viscosity would change the flow by less than about 1 % over one second of simulated time at the smallest cell (the per-step effect accumulated over the steps in a second). The per-liquid number is still printed. Replaces the per-step threshold 2.5e-4. (2026-11-15) |
| A45 | GPU memory budget | A share of the memory FREE when the run starts, not of the card's total, because other programs already hold some. The share is a named constant (start: 90 % of free). The grid's 25 % headroom stays (A37). (2026-11-15) |
| A46 | Solids in a viscous liquid | A guided rigid body holds its forbidden motion components during the solve (as planned). The viscous force and torque on every driven solid are added to the step report, next to the pressure force. (2026-11-15) |
| A47 | Wind | Acts on gas in the solver, and on the spray and foam particles of the render output. The liquid body is not pushed by wind. (2026-11-15) |
| A48 | Blender above 5.3 | Allowed, with one note that the add-on was tested with 5.3 only. No maximum version in the manifest. (2026-11-15) |
| A49 | CUDA runtime | The add-on package ships the CUDA runtime library it was built with. (2026-11-15) |
| A50 | Wind 'Flow' setting | A note only when the user changed Flow from its default 1.0. (2026-11-15) |
| A51 | The session link | Not in commit messages. Kept as a git note on each commit, following what the `git-ai` tool does (to be looked up and matched). (2026-11-15) |
| A52 | What decides cell size | Distance to the surface and to solids, surface curvature, and flow speed or shear, as the papers do it (literature check requested). Artist regions and a map were not selected: to confirm. (2026-11-15) |
| A53 | A viscous liquid against solids with prescribed motion | Sticks by default; each solid has a setting from full stick to free slip. An inviscid liquid slips with friction as before. (2026-11-15) |
| A54 | Paper fonts | Other MB Type fonts than Century Supra / Concourse / Triplicate: two sample pages to choose from. (2026-11-15) |
| A55 | Commit attribution, final | Replaces A39 and A51. Commit messages carry no AI trailer at all (no `Co-Authored-By`, no `Assisted-by`, no `Claude-Session`). Each commit has a plain git note in `refs/notes/claude-session` with two lines: `session: <link>` and `models: <model ids, comma separated>`. Git is configured to carry these notes across amend and rebase (`notes.rewriteRef`, `notes.rewriteMode cat_sort_uniq`). Notes stay local unless pushed on purpose. Not git-ai compatible (its line-level format cannot be written by hand); the Linux kernel removed its `Assisted-by` trailer in October 2026. (2026-11-15) |
| A56 | Paper fonts | Equity (text, 11 pt, about 70 characters per line), Hermes Maia (headings, captions, figure labels, procedure steps), Triplicate (code), with free fallbacks; chosen from rendered comparison sheets. Replaces Century Supra and Concourse. (2026-11-15) |
| A57 | Advice to set viscosity to 0 (replaces A44) | Compare with the method's own numerical smoothing (see literature-practice.md, topic 1): advise 0 when the liquid's viscosity is under a tenth of that smoothing, or when a feature four cells wide would change by less than 1 % over the run's duration. `check` prints both numbers and the Reynolds number, and says that viscosity 0 also switches the liquid from sticking to slipping along solids. The smoothing formula is the check's own derivation from a published filter analysis: state that in the paper. (2026-11-15) |
| A58 | GPU memory (refines A45, A43) | Budget = the smaller of 90 % of free and free minus 512 MiB, read after the GPU context exists. At the start a run reserves ONE GPU block sized by the plan (not the whole budget) and hands out pieces of it to every buffer; if limits are raised later it reserves another block, counted and reported. A warning for any requested byte beyond the estimate; a separate warning when the drop in free memory is smaller than what was reserved (Windows spilled into system memory), with a note about the driver's 'Prefer No Sysmem Fallback' setting. Tests may keep plain allocation. (2026-11-15) |
| A59 | Guided rigid bodies (refines A46) | The general form now: each guided body stores its allowed motions as a small matrix (any rail direction, any hinge point and axis), as in Batty 2007 and Aanjaneya 2018; hinges get a position correction after each step. (2026-11-15) |
| A60 | Force of the liquid on solids (refines A46) | For EVERY solid (free, guided, driven) the step report gives a pressure part and a viscous part read from the solve's own equations, whose sum is exactly the momentum exchanged: mean force and torque over the step, world axes, torque about the body's origin at the start of the step. Tests: sheared plate, buoyancy at rest, torque between rotating cylinders, settling sphere. (2026-11-15) |
| A61 | Cell size and the surface | First version: the surface always has the smallest cells. Curvature-driven coarse surface cells are a later, separate task (they need a surface pressure condition for size changes and careful resampling; Ando and Batty 2020). (2026-11-15) |
| A62 | Cell size from flow | A shear term relative to the scene's speed: wanted width = constant x reference speed / size of the velocity gradient; reference speed = the scene's largest liquid speed with a floor from gravity and the largest cell; starting constant 0.25, to calibrate. Not speed alone. (2026-11-15) |
| A63 | Cell size from the artist | Artist regions and a map are an input of the size rule (confirmed; they had been left unticked by oversight). So the shared rule's inputs are: depth below the surface, distance to solids, shear, artist regions and map; curvature later. Hysteresis as in literature-cell-size.md (split at once; merge only after 0.25 s and 8 steps with a 0.8 factor; never merge near the surface, air, gas or solids; one level per resize). (2026-11-15) |
| A64 | Deep liquid | First version: particles everywhere in the liquid (no grid-only deep region), so the reported energy loss of particle-free coarse cells and the unstable particle/grid velocity blend cannot occur. The grid-only region comes later as an optimisation, after an independent review of its design with two tests (a standing wave keeping its amplitude within a stated loss; stability at the edge of the particle band). (2026-11-15) |
| A65 | Particle size (reading of A64) | Particle size follows the cell: about eight particles per cell at every cell size (the particles and cell-resize designs' 1-to-8 split and 8-to-1 merge). Not one particle size everywhere. (2026-11-15) |
| A66 | Start state | A run starts on the adaptive grid: the start state is built with cell sizes already following the size rule, each cell seeded with particles of its own size, and the memory plan is sized on that start. (2026-11-15) |
| A67 | Particles that drift across a size change | At each cell-resize pass a particle whose size no longer matches its cell is split, or merged with neighbours; mass and momentum kept exactly, the kinetic-energy difference of a merge reported. (2026-11-15) |
| A68 | Large scenes, order after the first version | (1) test whether the fine surface band can shrink from 8 cells to 4; (2) coarse cells on calm surfaces plus batches cut by columns or tiles (removes the plan-area cap of slab batches); (3) the narrow band of particles, last. The first version keeps slab batches and the pinned surface. (2026-11-15) |
